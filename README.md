# TaskLine — служба поддержки клиентов в MAX (сервер)

Чат-бот поддержки в мессенджере MAX и мини-приложение для сотрудников: клиент пишет боту,
обращение попадает в очередь, ИИ сразу размечает его и подсказывает решение по похожим
закрытым случаям, сотрудник отвечает из мини-приложения — ответ приходит клиенту в тот же чат.

Решение состоит из двух репозиториев:

| Репозиторий                                                             | Что внутри                                                                                          |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| [TaskLine-server](https://github.com/bounchich1/TaskLine-server) (этот) | API, бот MAX, фоновые обработчики, ИИ-шлюз, Docker-конфигурация, OpenAPI, DATA-API, тестовые данные |
| [TaskLine-mini-app](https://github.com/bounchich1/TaskLine-mini-app)    | Мини-приложение сотрудников (React, MAX UI)                                                         |

Всё решение запускается одной командой из этого репозитория — см. [«Запуск в Docker»](#запуск-в-docker).

## Назначение

Небольшие и средние службы поддержки (на стенде — интернет-провайдер) получают обращения
в MAX без отдельного сайта и приложения:

- клиент пишет боту текст, фото, видео или файл — обращение с номером создаётся автоматически,
  данные обрабатываются только после согласия с политикой;
- ИИ определяет тему, срочность и сложность, предлагает шаги решения со ссылками на похожие
  решённые обращения и черновик ответа клиенту; сомнительные случаи помечает «нужна проверка»;
- сотрудники работают в мини-приложении внутри MAX: очередь по срочности, карточка обращения,
  ответы с файлами, передача коллеге, закрытие и переоткрытие, живое обновление;
- закрытые обращения пополняют базу знаний, и следующие подсказки становятся точнее;
- роли (сотрудник, руководитель, администратор), журнал аудита, настройки и шаблоны сообщений
  бота — без правки кода.

## Где попробовать в MAX

Рабочая версия развёрнута на демо-стенде и доступна весь период проверки:

- **чат-бот** — бот хакатона, выданный организаторами (ссылка — в карточке решения);
- **мини-приложение** — открывается кнопкой в чате бота, адрес `https://demo.juicymelons.top/`;
- **API** — `https://demo.juicymelons.top/v1/…`, спецификация — `https://demo.juicymelons.top/openapi.yaml`;
- **роли сотрудника** — команда `/code <КОД>` в чате бота; коды для ролей `support`,
  `supervisor` и `admin` переданы организаторам отдельно. Один аккаунт MAX может быть
  одновременно клиентом бота и сотрудником — удобно проверять обе стороны.

## Основной пользовательский сценарий

**Клиент (чат с ботом):**

1. Открывает бота и пишет вопрос. Бот просит согласие на обработку данных со ссылкой на
   политику и кнопками «Согласен» / «Отказаться». Сообщения до согласия хранятся
   зашифрованными и не обрабатываются.
2. После согласия бот сообщает: «Обращение №000001 создано. Сотрудник поддержки скоро ответит».
3. Клиент дописывает детали, присылает фото или файл — всё попадает в то же обращение.
4. Ответы сотрудника приходят в чат. После закрытия бот просит оценку от 1 до 10.
5. Под сообщениями бота — кнопки «Мои обращения», «Помощь» и «Отозвать согласие» (отзыв
   просит подтверждения). Те же действия — командами `/tickets`, `/help`, `/withdraw`; бот
   подсказывает их при вводе `/` (регистрирует команда `subscribe`).

**Сотрудник (мини-приложение):**

1. Открывает приложение кнопкой в чате бота — вход по подписанным данным запуска MAX,
   без паролей.
2. Видит очередь: новые обращения сверху по срочности, тема и сложность уже проставлены ИИ.
3. Открывает обращение: переписка с вложениями, подсказка ИИ (кратко, шаги, предостережения,
   ссылки на похожие решённые обращения) и черновик ответа.
4. Берёт обращение, при необходимости уточняет тему/срочность, отвечает клиенту (текст и файлы).
5. Закрывает обращение — клиенту уходит запрос оценки; при необходимости переоткрывает или
   передаёт коллеге с комментарием.

**Руководитель** дополнительно работает с чужими обращениями и видит «Состояние системы»
(фоновые задачи, доставки, память ИИ). **Администратор** дополнительно управляет сотрудниками,
справочниками, шаблонами сообщений бота, настройками организации и читает журнал аудита.

## Состав и архитектура

```
Клиент ──► бот MAX ──► POST /webhooks/max ──► api ──► PostgreSQL (входящие, обращения)
                                                │
                                   worker ◄─────┘  фоновые задачи (опрос БД + Redis/BullMQ)
                                     │  ├─► MAX Bot API: ответы клиентам, файлы
                                     │  └─► gateway ──► LLM (OpenAI-совместимый API)
                                     │                  └─► agentmemory (база решённых случаев)
Сотрудник ──► мини-приложение ──► /v1/* (REST + SSE /v1/events) ──► api
```

| Компонент                           | Назначение                                                                                                            | Где                              |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `api`                               | REST API для мини-приложения, вебхук бота, SSE-поток событий, `/health/*`, `/openapi.yaml`                            | этот репозиторий, роль `api`     |
| `worker`                            | обработка входящих, доставка ответов в MAX, скачивание и проверка файлов, ИИ-разбор, обучение, таймеры оценок         | этот репозиторий, роль `worker`  |
| `gateway`                           | единственный держатель ключа ИИ-провайдера, ограничение параллельных запросов, агент с инструментами поиска по памяти | этот репозиторий, роль `gateway` |
| `mini-app`                          | интерфейс сотрудников (React + MAX UI), статика за Caddy                                                              | репозиторий TaskLine-mini-app    |
| `web`                               | Caddy: единый адрес — `/v1`, `/webhooks`, `/health`, `/download` → `api`, остальное → `mini-app`                      | `compose.yaml`                   |
| PostgreSQL 18                       | все данные, очередь входящих и задач (outbox)                                                                         | Docker                           |
| Redis 7                             | очереди BullMQ и блокировки                                                                                           | Docker                           |
| ClamAV, SeaweedFS (S3), agentmemory | антивирус, хранилище файлов, память ИИ — в продакшн-стеке `deploy/compose.yaml`                                       | Docker                           |

Один образ сервера (`Dockerfile`) запускается в трёх ролях: `node dist/main.js api|worker|gateway`.
Код — модульный монолит; устройство модулей и правила зависимостей — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Запуск в Docker

Нужны Docker Engine 24+ (или Docker Desktop) с Docker Compose v2.24+ и доступ в интернет
(базовые образы, npm, GitHub — мини-приложение собирается из своего репозитория).

**Одна команда** (из корня этого репозитория):

```bash
docker compose up -d --build
```

Через 1–2 минуты откройте `http://localhost:8080`. Сборка обоих образов без кэша занимает
около минуты (без учёта загрузки базовых образов).

Что поднимется: `postgres`, `redis`, `migrate` (схема БД и справочники, завершается),
`seed` (загрузка тестовых данных, завершается), `api`, `worker`, `gateway`, `mini-app`, `web`.
Локальный стек работает без внешних сервисов: MAX и ИИ заменены заглушками (`MAX_MODE=mock`,
`AI_MODE=mock`), антивирус — заглушкой, файлы хранятся в томе `attachments`.

Состояние: `docker compose ps` — у `api` и `gateway` статус `healthy`, `migrate`, `seed` и
`files-init` — `exited (0)`.

Мини-приложение собирается из зафиксированного коммита репозитория TaskLine-mini-app. Чтобы
собрать его из локальной копии, укажите путь: `MINI_APP_SOURCE=../TaskLine-mini-app docker compose up -d --build`.

## Параметры окружения

- ОС: Linux, macOS или Windows 10/11 (Docker Desktop с WSL 2). Команды проверки ниже — для
  bash (на Windows — Git Bash или WSL).
- Ресурсы: 2 ядра, 2 ГБ свободной памяти, 2 ГБ диска под образы и тома.
- Свободные порты хоста: `8080`, `55432`, `6379` (меняются переменными, см. ниже).
- Открывайте приложение именно по `http://localhost:8080`: API принимает изменяющие запросы
  только с этого `Origin` (`APP_ORIGIN`).
- Продакшн: Linux-сервер с Docker, доменное имя с A-записью, открытые 80/443 (Caddy сам
  получает сертификат Let's Encrypt), бот MAX с токеном. Подробно — [runbooks/deploy.md](runbooks/deploy.md).

## Работа с данными

- **Хранение.** Все данные — в PostgreSQL: организация, сотрудники и сессии, клиенты и
  согласия, входящие сообщения, обращения и сообщения, закрытия и оценки, вложения, доставки,
  фоновые задачи, уведомления, аудит, справочники и шаблоны. Схема — `migrations/*.sql`,
  применяется командой `migrate`.
- **Согласие.** До согласия с политикой сообщения клиента хранятся только зашифрованными
  (AES-256-GCM, `ENCRYPTION_KEY`) и удаляются по истечении срока; без согласия обращения нет.
  `/withdraw` или кнопка «Отозвать согласие» с подтверждением отзывает согласие, закрывает
  обращение и исключает его из базы знаний.
- **Входящие.** Каждое обновление MAX сначала записывается в таблицу входящих (идемпотентно
  по ключу), затем обрабатывается `worker` строго по порядку для каждого клиента; после
  обработки зашифрованное содержимое удаляется.
- **Файлы.** Проверяются антивирусом и по сигнатуре типа, хранятся в закрытом S3-бакете,
  выдаются только сотрудникам или по одноразовой ссылке.
- **ИИ.** Ключ провайдера есть только у `gateway`. В модель уходит текст обращения только
  после согласия. Закрытые обращения сохраняются в agentmemory как «проблема → решение»;
  при переоткрытии обращения запись помечается устаревшей.
- **Безопасность.** Сессии и одноразовые ссылки хранятся хэшами; изменяющие запросы требуют
  CSRF-токен, `Origin` и ключ идемпотентности; конфликт версий — `409`; действия сотрудников
  пишутся в журнал аудита.

## Тестовые данные и учётные записи

Тестовые данные — синтетические клиенты интернет-провайдера (MAX ID `9100000001`–`9100000106`).
Им выдаётся согласие, их сообщения проходят обычный путь входящих, а сообщения бота и
сотрудников им в MAX **не отправляются**: доставка имитируется (`delivery_state: "delivered"`,
ссылка `synthetic-…`). Реального клиента загрузчик не трогает.

- [`test-data/resolved-cases.json`](test-data/resolved-cases.json) — 6 решённых обращений
  (нет интернета, скорость по Wi-Fi, платёж, обрывы, переезд, личный кабинет): вопрос клиента,
  ответ сотрудника с решением, подтверждение клиента и оценка. Загрузчик берёт в работу, отвечает
  и закрывает их от имени первого администратора, который уже входил в приложение (без него
  история пропускается), и ждёт, пока ИИ разберёт их и сохранит в базу знаний (`learned`).
- [`test-data/max-updates.json`](test-data/max-updates.json) — 7 сообщений от 6 новых клиентов
  на те же темы в формате обновлений MAX `message_created`. Становятся 6 открытыми обращениями;
  загрузчик заводит их по одному и ждёт разбора ИИ (у разбора есть 2 минуты), поэтому подсказки
  ссылаются на решённые случаи. В конце печатает по каждому: статус ИИ, тему/срочность/сложность,
  число шагов и процитированных случаев.

Загрузка — команда `seed-test-data` (локально её сразу выполняет сервис `seed`). Повторный
запуск ничего не дублирует:

```bash
docker compose run --rm seed
```

Свой файл открытых обращений того же формата: `docker compose run --rm api node dist/cli.js seed-test-data <путь>`.
В production-режиме загрузка разрешена только на демо-стенде (задан `DEMO_ROLE_CODES`).
**На демо-стенде данные уже загружены** реальным ИИ: в очереди 6 новых обращений с подсказками,
во вкладке «Закрытые» — 6 решённых.

- [`test-data/webhook-role-code.json`](test-data/webhook-role-code.json) — сообщение `/code`
  от пользователя MAX `1001` для локальной выдачи роли.
- **Учётные записи.** Паролей нет: сотрудник — это аккаунт MAX с ролью. На демо-стенде роль
  выдаёт команда `/code <КОД>` в чате бота (коды переданы организаторам). Локально коды:
  `LOCAL-SUPPORT-CODE`, `LOCAL-SUPERVISOR-CODE`, `LOCAL-ADMIN-CODE`.

## Пошаговый сценарий проверки

### В MAX (демо-стенд)

1. Найдите бота организаторов в MAX и нажмите «Начать». Отправьте `/code <КОД_SUPPORT>` и откройте
   мини-приложение кнопкой в чате: в очереди уже 6 демо-обращений с подсказками ИИ — шаги со
   ссылками на решённые случаи из вкладки «Закрытые» и черновик ответа клиенту.
2. Напишите вопрос, например: «Нет интернета со вчера, роутер мигает красным». Бот попросит
   согласие — нажмите «Согласен». Бот ответит «Обращение №… создано».
3. Отправьте в тот же чат фото — оно попадёт в обращение.
4. Откройте мини-приложение заново кнопкой в чате. В очереди — ваше обращение с темой и срочностью
   от ИИ; в карточке — подсказка ИИ и черновик ответа.
5. Нажмите «Взять в работу», ответьте клиенту — ответ придёт вам в чат бота.
6. Закройте обращение — бот попросит оценку, отправьте число от 1 до 10.
7. Отправьте `/code <КОД_ADMIN>`, откройте приложение заново — появятся «Управление» и
   «Состояние системы»: сотрудники, справочники, шаблоны, настройки, аудит.
8. Напишите боту новый вопрос, похожий на закрытый, — в подсказке появится ссылка на прошлое
   обращение (база знаний пополняется после закрытия; нужна включённая память ИИ).

### Локально в Docker

```bash
docker compose up -d --build
docker compose ps
curl -s http://localhost:8080/health/ready
```

Ожидается `{"status":"ready","version":"local"}`.

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://localhost:8080/openapi.yaml
```

Откройте `http://localhost:8080` — через несколько секунд мини-приложение покажет «Вход не
выполнен. Откройте мини-приложение через бота в MAX…»: вне MAX вход невозможен, это ожидаемо.
Дальше проверяем API.

Выдайте пользователю MAX `1001` роль администратора — так же, как это делает бот:

```bash
curl -s -X POST http://localhost:8080/webhooks/max -H "Content-Type: application/json" -H "X-Max-Bot-Api-Secret: local-webhook-secret-not-for-production" --data-binary @test-data/webhook-role-code.json
```

Войдите за этого пользователя (локальный вход без MAX работает только изнутри контейнера):

```bash
docker compose exec api wget -qO- --header "Content-Type: application/json" --header "Origin: http://localhost:8080" --post-data '{"user_id":"1001"}' http://127.0.0.1:3000/v1/auth/dev
```

Из ответа возьмите `token` и `csrf`:

```bash
TOKEN=<token>
CSRF=<csrf>
curl -s "http://localhost:8080/v1/tickets?status=open" -H "Authorization: Bearer $TOKEN"
```

В ответе 6 обращений из тестовых данных. Решённые случаи загружаются, когда в системе есть
администратор, который уже входил, — после двух шагов выше выполните `docker compose run --rm seed`,
и во вкладке `?tab=closed` появятся 6 закрытых обращений с оценками.

Возьмите `id` и `version` первого открытого обращения и выполните команды:

```bash
ID=<id>
curl -s -X POST http://localhost:8080/v1/tickets/$ID/assign -H "Authorization: Bearer $TOKEN" -H "X-CSRF-Token: $CSRF" -H "Origin: http://localhost:8080" -H "Idempotency-Key: check-assign-1" -H "If-Match: <version>" -H "Content-Type: application/json" -d '{}'
curl -s -X POST http://localhost:8080/v1/tickets/$ID/messages -H "Authorization: Bearer $TOKEN" -H "X-CSRF-Token: $CSRF" -H "Origin: http://localhost:8080" -H "Idempotency-Key: check-reply-1" -H "If-Match: <новая version>" -H "Content-Type: application/json" -d '{"text":"Проверяем линию"}'
curl -s "http://localhost:8080/v1/tickets/$ID/messages" -H "Authorization: Bearer $TOKEN"
```

Ответ `assign` — обращение со `status: "in_progress"`, ответ на сообщение — код `202`; в
переписке появятся сообщение клиента, автоответ бота и ваш ответ с `delivery_state: "delivered"`
(доставлен заглушкой MAX). Закрытие — `POST /v1/tickets/$ID/close` с актуальной версией.

## Примеры ожидаемого поведения

| Действие                                  | Ожидаемый результат                                                                                                     |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `GET /health/ready`                       | `200 {"status":"ready","version":"…"}`                                                                                  |
| Первое сообщение клиента боту             | кнопки согласия и текст «Для обращения в поддержку необходимо согласие на обработку данных. Политика: …»                |
| «Согласен»                                | «Согласие принято…», затем «Обращение №000001 создано. Сотрудник поддержки скоро ответит.»                              |
| `/code <верный код>`                      | «Роль «Администратор» выдана. Откройте приложение кнопкой в этом чате…»                                                 |
| `/code <неверный код>`                    | «Код не подошёл. Отправьте его одним сообщением: /code ВАШ-КОД»                                                         |
| `GET /v1/tickets` без токена              | `401 {"code":"unauthorized","message":"Сессия истекла. Откройте приложение заново.",…}`                                 |
| `GET /v1/admin/employees` ролью `support` | `403 {"code":"forbidden",…}`                                                                                            |
| Команда с устаревшим `If-Match`           | `409 {"code":"ticket_version_conflict",…}`                                                                              |
| `POST` без `Origin`                       | `403 {"code":"origin_denied",…}`                                                                                        |
| `POST /v1/tickets/{id}/messages`          | `202`, клиент получает ответ в чате MAX                                                                                 |
| `POST /v1/tickets/{id}/close`             | `200`, `status: "awaiting_rating"`, клиенту — «Обращение №… закрыто. Оцените работу поддержки целым числом от 1 до 10.» |

## Известные ограничения

- Локально нет настоящего MAX: ответы бота «доставляет» заглушка (видно по `delivery_state`),
  а вход в мини-приложение возможен только внутри MAX. Полный сценарий проверяется на демо-стенде.
- Для реального бота нужен публичный HTTPS-адрес вебхука — на локальной машине без туннеля
  он недоступен.
- ИИ-заглушка всегда «не уверена»: обращения получают тему «Не определён» и отметку «нужна
  проверка». Настоящие подсказки — с ключом провайдера (`AI_MODE=live`).
- База знаний (agentmemory), антивирус и S3 в локальном стеке выключены (есть профили
  `memory`, `files`, `s3` для разработки); вложения проверяются заглушкой и хранятся в томе.
- Демо-обращения — от синтетических клиентов: ответы им не уходят в MAX, доставка имитируется.
- Одна организация на установку. Роли по кодам — только для демо-стенда: любой, кто знает код,
  получает роль.
- Сессия сотрудника — до 8 часов и завершается после 30 минут бездействия; строка запуска MAX
  действует 5 минут.
- Хосты видео и документов MAX пока не подтверждены — на стенде разрешён только `i.oneme.ru`;
  файлы с других хостов помечаются «недоступно».

## Остановка и повторный запуск

```bash
docker compose stop            # остановить, данные сохраняются
docker compose start           # запустить снова
docker compose down            # удалить контейнеры, тома с данными остаются
docker compose up -d           # поднять снова с теми же данными
docker compose up -d --build   # пересобрать образы после изменений кода
docker compose down -v         # удалить всё, включая данные; следующий up начнёт с нуля
```

Журналы: `docker compose logs -f api worker gateway`.

## API: OpenAPI и DATA-API

- [openapi.yaml](openapi.yaml) — OpenAPI 3.1, все маршруты с форматами запросов и ответов
  (тест `tests/routes.test.ts` не даёт добавить маршрут без описания); та же спецификация —
  `GET /openapi.yaml`.
- [DATA-API.yaml](DATA-API.yaml) — обязательные проверки для платформы оценки: базовый адрес,
  роли и получение токена, 28 проверок с методами, параметрами, ожидаемыми кодами и полями.

Формат запросов: `Authorization: Bearer <token>`; для всех методов, кроме GET, — `Origin`,
`X-CSRF-Token` и `Idempotency-Key`; для команд над обращением и настроек — `If-Match: <version>`.
Ошибки: `{"code","message","request_id","retryable"}`.

## Разработка

```bash
npm install
npm run env:init          # создаёт .env с локальными секретами
docker compose up -d postgres redis
npm run db:migrate
npm run dev:all           # api + worker + gateway в одном процессе (заглушки MAX и ИИ)
```

Роли по отдельности: `npm run dev` (api), `npm run worker`, `npm run gateway`.
Проверки: `npm run check` (форматирование, ESLint, типы, knip, тесты, сборка);
`RUN_POSTGRES_TESTS=1 npm run test:integration` — с PostgreSQL из compose.

Изменение схемы — новый файл `migrations/NNN_name.sql` со следующим номером; выпущенные
миграции не редактируются.
